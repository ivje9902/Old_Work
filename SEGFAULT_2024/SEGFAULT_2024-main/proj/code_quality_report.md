# Code quality report SEGFAULT

One of the most important parts of any program is the readability of the code. If another developer cannot understand what problems the programs are solving and how then it becomes difficult for that individual to work with the code.

## Tools
Some tools that we used to ensure that our code held a good standard was code reviews, testing and the code standard Apache. Code reviews helped us control the code before it was merged with the main branch. We go into more detail on this topic in the [code review report](code_review_report.md), but to summarize, the reviews we performed on all every piece of code ensured that our code held a high standard and performed as we expected. If there was a piece of code that did not follow our code standard or that we felt was written poorly, we simply issued a push-back and had the coder rewrite the code again. Testing is also a big part of checking not only that the function works, but more importantly that the function works like the specification says that it does. If a function does not match the specification than a new developer might use it in a way that the function does not support.

## Code standard
We did not put a lot of time into deciding what code standard to use, since they all fill the same purpose with only slight differences. In the end Apache was chosen because we felt that it did not interfere too much with how we were used to writing code, since the changes between this standard and what we had been taught during other courses was very minimal. A code standard itself does not really ensure that code works, but it does help with readability. Writing code with a specific standard that is known to the user makes it easy to understand what code belongs to what functions. Using a code standard also helped in the code review because we had a template where we could check if a piece of code was actually correctly written according to the standard. Lastly it removes the problems that can come from people with different code standards trying merge code together, which could lead to a .c file that is hard to read and understand because different functions are written in different ways.

## Naming conventions
We decided to follow a convention where we only used lowercase letters for naming functions and variables. If any functions contained more than one word, we used underlines to separate the words, for example the function set_cascade_limit. This function also shows our convention regarding the structure of functions with a specific task. If the name of the function contained a verb such as set, get, or allocate we made sure to put that at the beginning of the function to increase readability. When necessary, we implemented the use of ioopm at the start of functions to show that these functions were from earlier in the course, such as the ioopm_linked_list function.

This use of ioopm names did come with a few problems when we started to implement inlupp 2. Since we had allready implemented some functions from earlier in the course that were not static there arose some naming errors because functions shared the same name. To work around this, we added _demo to all the non-static functions from inlupp 2 so they no longer clashed with our own functions.

For testing we decided to write test_ followed by the name of the function being tested, and lastly what we specifically tested if that information was needed. For example, when we tested allocating ints we named the test test_allocate_int.

## Readability and maintenance
The chosen code standard was helpful when it came to maintaining the code. If we realised later on in the project that a finished function needed to be changed in order to work correctly, we could change that function more easily because it was written using a fixed coding standard. It allowed any member of the team to update necessary functions regardless of their prior knowledge of the function, and significantly sped up the process of updating the project to work with functions that were added later on.

Since the project involved a lot of people working in parallel, we decided to build each function separately and then merge them together in main. Implementing each function individually allows us to be more precise when it comes to testing and code reviews. If we were to let someone implement a large set and functions at the same time it would damage the readability and small problems would have a higher chance of slipping through to the main branch.

## Testing
Testing was something we knew needed to be done on the program in order to make sure that the functions were working correctly. Unfortunately, time constraints prevented us from working with a test-driven approach, which resulted in us making the tests after the functions had already been implemented. The tests did still prove useful as they provide an easy way to check if the implementation was correct. To make the testing as unbiased as possible we chose to make the person in charge of the tests not be the same one that implements the functions. This requires that everyone that writes functions to write clear comments so that the tester knows what properties of the functions that needs testing, what the edge cases are, and lastly what could cause the functions to behave irrationally. We go more in depth about how we used testing to control the quality of the code in the [test report](test_report.md).

## Reflection
All these requirements for the code did come with some consequences. Because of the many reviews and rules each piece of code had to follow, it took longer to approve code for merging than it would have if we allowed every member to write with whatever code standard they wanted. Many members were also not familiar with this coding standard, so it was quite common for pull requests to receive push backs because of code standard requirements or general readability. Although in the end we feel that this approach has led to a more secure code that every member of the team understands and can work on later on, whether it be testing or improving the functionality of the program.
