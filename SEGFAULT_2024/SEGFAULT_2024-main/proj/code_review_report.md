# Code review report SEGFAULT

## Pull request log
[GitHub Pull request log](https://github.com/IOOPM-UU/SEGFAULT/pulls)

## Report

To ensure that all the code that is merged onto the main branch is working and written correctly we used pull requests for every piece of new code. When a member is finished writing a piece of code, they committed it to their respective branch and issued a “pull request”, this means that the code is ready for review but has not yet been merged with the main branch. Afterwards the developer requested a review from someone in the group. The reviewer's job was to read through the implementation and point out anything and everything that needed or could be changed. No changes were too small and something as small as writing in comments or return types were reviewed. If the code needed changes the reviewer could request a change. Which meant that the developer needed to rewrite some part and the code and commit it again. When the reviewer felt that everything was correct, they could merge it with the main branch. Making it available for everyone in the group to see. Because of our high demand on the commited code there were quite a few pushbacks, but these were mostly minor things such as spelling errors and what not. But every once in a while, there were some larger problem or design that needed changing in order to fit with the rest of the code.

This method of reviewing code ensured that nobody reviewed their own code, and nothing was directly merged to main without at least input from another member. Having members review their own code can be detrimental since they themselves know how the function works and can therefore miss simple issues that they did not think about. It is especially important comments to functions are reviewed by another person as they will see the function comments without knowing how it works. This allows the reviewer to easily spot lacking explanations about implementations or specific values.

As the project went on and new functions were added to the .c file we continuously reviewed old functions to see if they needed to be updated in order to accommodate the new functions and improve readability among other things.

Another step we took to simplify the review process was to have every new function be on a separate branch. This made the review process easier as the reviewer only had to review one function at a time. One could argue that this method slows down the implementation process because every new function needs to be reviewed individually before they can be merged with the main branch. That meant functions that built upon older functions which had not been merged yet could not use the them since they technically did not exist yet on that branch. Taking this into consideration we still felt that this was a worthwhile trade-off to ensure that the code we merged was of the highest possible quality. In the end no pull request sat for more than a couple of days before being reviewed, with Christmas break being the main reason for most the delays.

We had not discussed any specific code review checklist, so it was up to each reviewer to search the code as they saw fit. A reason for this is partly because all the commits where different so a single fixed checklist might not cover everything and only be a hindrance instead of a tool. The second part would be that we simply did not discuss anything regarding the code review other than that we would try to look over them as soon as possible. This might have resulted in people having slightly different approaches to code review, but the accuracy was the same for different members, which was all we wanted.

For those that were more familiar with code review on GitHub it was easy to start but for some there required some getting used to in order to start reviewing at a higher level. The colourful diffs were harder to understand in the beginning but in the end when people grew more comfortable it was a great tool to help speed up the process. Instead of reading through the entire file you just needed to check newly added code and review those parts.

Taking a look back on the process, we ended with 31 pull requests which may not feel like a lot but since we compacted every function into a singular pull request, we still feel this number provides a good image of our review process. We feel that this method of working has greatly improved the quality of the code in the main branch and if we were to restart the project again, we would not change anything regarding our code review process.
